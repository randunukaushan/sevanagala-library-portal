# Information Architecture and Sitemap

## 1. Purpose

### 1.1 Objective

Define how public information, donor information, development needs, library resources, and staff workflows are organised so visitors can find what they need quickly.

### 1.2 Design Principle

Navigation must be understandable to:

- local readers;
- students;
- parents;
- library staff;
- international donors;
- corporate CSR teams;
- NGOs and foundations;
- public authorities.

The website should not expose internal administrative complexity in the public navigation.

## 2. Primary Navigation

### 2.1 Recommended Top-Level Navigation

1. Home
2. About
3. Services
4. Books & Resources
5. Current Needs
6. Projects
7. Support & Partner
8. Transparency
9. News
10. Contact

On small screens, these items may be grouped into a compact mobile menu.

### 2.2 Home

The Home page should contain:

- library identity;
- short mission statement;
- opening information;
- major services;
- current top needs;
- active development projects;
- latest updates;
- recent verified support;
- clear calls to action.

Primary calls to action:

- Explore the Library
- View Current Needs
- Support a Project
- Contact the Library

### 2.3 About

Recommended pages:

- About the Library
- History
- Community Served
- Library Team
- Governance / Administration
- Opening Hours and Location

Staff names should only be published when officially approved.

### 2.4 Services

Possible service cards:

- book lending;
- reference reading;
- children's section;
- student study areas;
- newspapers and periodicals;
- exam-support resources;
- computers and digital access when available;
- reading programmes;
- future smart-library services.

### 2.5 Books & Resources

Recommended structure:

- Browse Categories
- New Arrivals
- Requested Books
- Student Resources
- O/L Resources
- A/L Resources
- English Learning
- STEM and Technology
- Digital Resources
- Search Catalogue — activate when verified catalogue data or an approved integration is ready

### 2.6 Current Needs

Recommended filters:

- Books
- Furniture
- Computers
- Internet & Networking
- Smart Library
- Children's Area
- Accessibility
- Infrastructure
- Other

Filter by status:

- Seeking Support
- Partially Supported
- Fully Pledged
- Received
- Completed

### 2.7 Projects

Project examples:

- Book Collection Renewal
- Digital Learning Corner
- Public Wi-Fi
- Computer Lab
- Children's Reading Area
- Furniture Improvement
- Smart Library Development

Each project may contain multiple needs.

### 2.8 Support & Partner

Recommended sections:

- How to Support
- Donate Books
- Support Equipment or Facilities
- Become a Partner
- International Organisations
- Corporate / CSR Partnerships
- Contact the Library

V1 should use enquiry and coordination workflows, not online cash collection.

### 2.9 Transparency

Recommended pages:

- Needs Tracker
- Donations & Pledges
- Completed Projects
- Partner Acknowledgements
- Impact Updates
- Methodology / How Statuses Work

### 2.10 News

Content types:

- library updates;
- new books;
- project milestones;
- donor deliveries;
- events;
- service notices.

### 2.11 Contact

Show:

- approved official address;
- approved phone numbers;
- approved email;
- opening hours;
- map only after the official location is confirmed;
- contact form;
- accessibility contact where relevant.

## 3. User Journeys

### 3.1 Reader Journey

Home → Books & Resources → Category or Resource → Availability / Request Guidance → Contact or Visit Library.

### 3.2 Student Journey

Home → Student Resources → O/L or A/L / STEM / English → Useful Resources → Library Visit or Request.

### 3.3 Donor Journey

Home → Current Needs → Need Detail → Related Project → Transparency Evidence → Support & Partner → Enquiry.

### 3.4 Corporate CSR Journey

Home → Projects → Project Detail → Remaining Needs → Past Impact → Partnership Information → Contact.

### 3.5 Library Staff Journey

Admin Login → Dashboard → Select Content Type → Create/Edit → Review → Publish.

### 3.6 Content Approver Journey

Admin Login → Pending Changes → Review → Approve / Reject → Publish → Audit Entry.

## 4. Need Detail Page

### 4.1 Required Public Fields

A need page should show:

- title;
- category;
- short description;
- purpose;
- target quantity;
- pledged quantity;
- received quantity;
- remaining quantity;
- status;
- priority;
- related project;
- last verified date;
- support contact path.

### 4.2 Optional Fields

May include:

- estimated unit cost;
- technical specifications;
- accepted alternatives;
- target age group;
- language;
- supporting photo;
- reference document.

### 4.3 What Not to Show

Do not show:

- private donor negotiations;
- personal phone numbers without approval;
- internal notes;
- supplier quotations unless publication is approved;
- unverified values;
- sensitive administrative documents.

## 5. Project Detail Page

### 5.1 Required Sections

A project page should include:

- problem statement;
- project objective;
- community benefit;
- current stage;
- related needs;
- verified support;
- remaining gaps;
- milestones;
- project updates;
- last verified date.

### 5.2 Project Lifecycle

Recommended public lifecycle:

- Planned
- Approved
- Seeking Support
- In Progress
- Completed
- Archived

## 6. Partner Page

### 6.1 Public Partner Record

With explicit permission:

- organisation name;
- country;
- website;
- logo;
- contribution summary;
- related project;
- verified date;
- impact update.

### 6.2 Recognition Principle

Recognition is acknowledgement of support, not an endorsement of the organisation, product, service, or political position.

## 7. Multilingual Information Architecture

### 7.1 Locale Model

Recommended route structure:

- /si/...
- /en/...
- /ta/...

### 7.2 Content Rules

Each content record should support translated:

- title;
- summary;
- body;
- metadata;
- alt text where needed.

### 7.3 Fallback Rules

If a translation is unavailable:

- do not silently pretend the content is translated;
- display the approved fallback language;
- optionally show "translation pending".

## 8. Search and Filtering

### 8.1 Search Priorities

Search should progressively support two distinct discovery needs:

Public-site search:

- needs;
- projects;
- news;
- services;
- approved pages.

Library catalogue search, when verified catalogue data or an approved library-system integration is available:

- title;
- author;
- ISBN;
- keyword;
- subject;
- category;
- language.

Catalogue discovery should become a primary reader journey as soon as the data quality and authoritative availability source are sufficient.

### 8.2 Filters

Public-content filters may include:

- category;
- status;
- project;
- date;
- priority where appropriate.

Catalogue filters may include:

- language;
- category / subject;
- author;
- audience or age group;
- item type / format;
- collection;
- availability;
- publication year;
- shelving location where reliable.

Progressive disclosure should keep the default mobile search simple while making advanced filters available when needed.

### 8.3 Search Privacy

Do not log personally identifiable search histories unless there is a documented need and an approved retention policy.

## 9. Footer Architecture

### 9.1 Required Footer Content

Include:

- library name;
- official address;
- opening hours;
- contact;
- quick links;
- privacy notice;
- accessibility statement;
- transparency methodology;
- copyright / content ownership notice.

### 9.2 Conditional Items

Only after approval:

- local authority name;
- official logos;
- social-media links;
- official registration or administrative information.

## 10. SEO and Discoverability

### 10.1 Page Metadata

Every public page should have:

- unique title;
- meaningful description;
- canonical URL;
- social preview metadata where useful.

### 10.2 Structured Content

Use semantic HTML, correct heading hierarchy, descriptive links, and sitemap generation.

### 10.3 Donor Discoverability

English project and needs pages should use clear descriptive language such as:

- public library development;
- rural community library;
- book donation needs;
- digital learning;
- computer access;
- library partnership.

Avoid exaggerated or unverifiable claims.

## 11. Low-Bandwidth Design

### 11.1 Performance

Prioritise:

- compressed images;
- responsive images;
- minimal third-party scripts;
- server-rendered public pages where appropriate;
- caching;
- simple mobile layouts.

### 11.2 Progressive Enhancement

Core information must remain readable even if advanced JavaScript features fail.

## 14. Reader-Facing Smart Library Expansion

### 14.1 Catalogue

A future or phased catalogue area should include:

- simple search;
- advanced search;
- browse by category;
- new arrivals;
- popular or highlighted titles where data is reliable;
- book detail pages;
- copy/holding information;
- shelf or section information;
- hold/reserve actions only when supported by the authoritative system.

### 14.2 My Library

When member integration is approved, a private My Library area may contain:

- current loans;
- due dates;
- eligible renewals;
- holds/reservations;
- saved books or lists;
- notifications;
- membership information.

Sensitive information must remain authenticated and role-protected.

### 14.3 Children's Experience

The information architecture should be able to support a dedicated children's discovery area without making the whole site visually childish.

Potential entry points include:

- age groups;
- recommended collections;
- new children's books;
- reading programmes;
- events;
- reading challenges.

### 14.4 Events and Announcements

Events and announcements should remain first-class library content rather than being hidden inside general news.

### 14.5 Mobile Navigation

On narrow screens, prioritise the most common reader tasks:

1. Search books;
2. Home;
3. Books / Resources;
4. Services;
5. My Library when available.

Lower-frequency institutional, donor, and transparency destinations can remain accessible through the menu without competing with core reader actions.

### 14.6 Multi-Library Discovery

When more libraries join, the same information architecture should be able to show:

Book → Holdings → Library → Section → Shelf / location.

The single-library Sevanagala experience should remain clear even when the underlying architecture becomes multi-library capable.

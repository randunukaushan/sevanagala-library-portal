# Operations, Maintenance and Staff Handover

## 1. Purpose

### 1.1 Objective

Define how the portal remains usable, secure, current, and maintainable after launch.

## 2. Operational Ownership

### 2.1 Content Owner

Responsible for:

- public information;
- needs;
- project updates;
- donor acknowledgements.

### 2.2 Technical Maintainer

Responsible for:

- deployment;
- security updates;
- backups;
- incidents;
- domain/DNS.

### 2.3 Data Owner

Responsible for:

- collection quality;
- donor data;
- retention;
- corrections.

## 3. Routine Schedule

### 3.1 Daily or As Needed

Review:

- urgent contact messages (if a public enquiry path is enabled);
- system errors;
- donation receipts.

### 3.2 Weekly

Review:

- open enquiries (if a public enquiry path is enabled);
- pending pledges;
- active needs.

### 3.3 Monthly

Review:

- stale needs;
- project progress;
- broken links;
- dormant accounts;
- storage usage.

### 3.4 Quarterly

Review:

- permissions;
- dependencies;
- privacy;
- accessibility;
- backup recovery.

## 4. Staff Handover

### 4.1 Required Materials

Provide:

- admin guide;
- role guide;
- login process;
- content workflow;
- donor workflow;
- backup process;
- incident contact.

### 4.2 Training

Train staff to:

- create/update needs;
- record donations;
- publish news;
- manage book requests;
- avoid publishing private data.

If circulation is approved, add a practice environment and short task guide for member lookup, item lookup/scan, issue, return and common exceptions. Train staff not to share accounts, bypass blocked rules or put reader details in free-text notes. Assign named owners for policy changes, account removal, privacy requests, recovery and incident escalation. Do not introduce offline circulation until there is a tested reconciliation and duplicate/conflict procedure; a benchmark system's offline feature is not a local operating plan.

## 5. Account Management

### 5.1 New Staff

Create unique account with minimum role.

### 5.2 Leaving Staff

Disable access promptly.

### 5.3 Shared Accounts

Do not use shared admin passwords.

## 6. Content Freshness

### 6.1 Needs

Each active need should have a last-verified date.

### 6.2 Opening Hours

Update immediately when permanently changed.

### 6.3 Contacts

Review periodically.

## 7. Backup Operations

### 7.1 Database

Confirm backups are running.

### 7.2 Restore

Test restore periodically.

### 7.3 Exports

Maintain export capability for critical data.

## 8. Security Maintenance

### 8.1 Dependencies

Apply reviewed security updates.

### 8.2 Secrets

Rotate after exposure or personnel change where needed.

### 8.3 Audit

Review privileged activity when relevant.

## 9. Incident Handling

### 9.1 Examples

- admin account compromised;
- private file exposed;
- wrong donor claim;
- database failure;
- defacement.

### 9.2 Response

- contain;
- preserve evidence;
- correct;
- notify authority;
- restore;
- document.

## 10. Service Continuity

### 10.1 Critical Information

Keep offline copies of:

- key contacts;
- domain ownership;
- hosting ownership;
- recovery instructions.

## 11. Vendor Dependency

### 11.1 Rule

Document how to export data from:

- Vercel;
- Supabase;
- GitHub.

Avoid lock-in where practical.

## 12. Cost Review

### 12.1 Monthly

Track:

- hosting;
- database;
- storage;
- domain;
- email;
- internet-related service costs.

## 13. Documentation Maintenance

### 13.1 Rule

Docs should reflect production reality.

### 13.2 Update Trigger

Update docs when:

- workflow changes;
- role changes;
- provider changes;
- new feature changes policy.

## 14. Handover Acceptance

### 14.1 Complete When

- institutional owners know accounts;
- staff can operate portal;
- technical recovery is documented;
- credentials are safely transferred;
- support contact is known.
